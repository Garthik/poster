## 1. Реализовать отчёт с `$lookup` и `$unwind`.

Редактору афиши нужны десять опубликованных гидов с наибольшим числом одобренных отзывов. Конвейер агрегации сначала считает отзывы каждой страницы, затем получает её заголовок и номер события. Такое соединение выполняется один раз на страницу.

> **Конвейер агрегации** передаёт документы от одного этапа обработки к следующему. **$lookup** находит связанные документы в другой коллекции и возвращает массив. **$unwind** разворачивает массив в отдельные строки.

В Compass откройте `visitor_feedback → Aggregations → Text`, вставьте весь массив и нажмите **Run**. Итог сначала отсортирован по числу отзывов, при равенстве — по идентификатору страницы.

```json
[
  {"$match": {"moderation": "approved"}},
  {"$group": {"_id": "$pageSlug", "reviews": {"$sum": 1},
              "averageRating": {"$avg": "$rating"}}},
  {"$lookup": {"from": "event_pages", "localField": "_id",
               "foreignField": "_id", "as": "page"}},
  {"$unwind": "$page"},
  {"$match": {"page.status": "published"}},
  {"$project": {"_id": 1, "headline": "$page.headline",
                "pgEventId": "$page.pgEventId", "reviews": 1,
                "averageRating": {"$round": ["$averageRating", 2]}}},
  {"$sort": {"reviews": -1, "_id": 1}},
  {"$limit": 10}
]
```

| Первые три строки | Заголовок | Отзывы | Средняя оценка |
|---|---|---|---|
| s7-page-0003 | Гид по мероприятию 0003 | 648 | 3,05 |
| s7-page-0015 | Гид по мероприятию 0015 | 639 | 2,95 |
| s7-page-0013 | Гид по мероприятию 0013 | 630 | 2,97 |

Проверка проведена на 65 536 воспроизводимых учебных отзывах и 1 025 страницах. Идентификаторы событий взяты из снимка PostgreSQL проекта. Страницы и отзывы сгенерированы для опыта. ## 2. Реализовать отчёт с `$facet` или `$bucket`.

Модератору нужны две сводки. Первая показывает, сколько отзывов ожидают решения, одобрены или отклонены. Вторая показывает распределение оценок от 1 до 5 среди одобренных. Оба расчёта получают один и тот же входной набор.

> **$facet** запускает несколько ветвей обработки над одними входными документами. Каждая ветвь записывает свой результат в отдельный массив итогового документа. **$bucket** группирует значения по заданным интервалам. Для двух независимых сводок выбран `$facet`.

В Compass откройте `visitor_feedback → Aggregations → Text` и выполните запрос. Фильтр по одобрению расположен внутри второй ветви, поэтому первая сохраняет все статусы.

```json
[
  {"$facet": {
    "byStatus": [
      {"$group": {"_id": "$moderation", "count": {"$sum": 1}}},
      {"$sort": {"count": -1, "_id": 1}}
    ],
    "approvedRatings": [
      {"$match": {"moderation": "approved"}},
      {"$group": {"_id": "$rating", "count": {"$sum": 1}}},
      {"$sort": {"_id": 1}}
    ]
  }}
]
```

| Статус | Одобрены | На проверке | Отклонены | Всего |
|---|---|---|---|---|
| Число отзывов | 45 948 | 13 015 | 6 573 | 65 536 |

| Оценка | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| Одобренные отзывы | 8 989 | 9 290 | 9 172 | 9 197 | 9 300 |

Сумма пяти столбцов равна 45 948. Так можно проверить, что во вторую ветвь попали все одобренные отзывы. [Конвейер](../../mongo/lab7/pipelines/moderation.json) · [Результат обеих ветвей](../../artifacts/lab7/template/reports.json)

## 3. Создать отдельную коллекцию с предварительно рассчитанным отчётом через aggregation pipeline и `$merge`.

В коллекции `page_feedback_report` хранится одна строка на каждый гид, включая черновики и страницы без отзывов. Поля `reviews` и `ratingSum` хранят число одобренных отзывов и сумму их оценок. Средняя оценка при нуле отзывов равна `null`.

> **Материализованный отчёт** — сохранённый результат вычисления, который можно сразу прочитать. **$merge** записывает результат конвейера в коллекцию и определяет способ обработки совпадений по ключу.

В Compass откройте `event_pages → Aggregations → Text`. Нажмите **Run** и подтвердите запись, если появится диалог. По `_id` новая строка добавляется, существующая заменяется.

```json
[
  {"$lookup": {"from": "visitor_feedback", "localField": "_id",
    "foreignField": "pageSlug", "pipeline": [
      {"$match": {"moderation": "approved"}},
      {"$group": {"_id": null, "n": {"$sum": 1},
                  "points": {"$sum": "$rating"}}}
    ], "as": "counts"}},
  {"$project": {"_id": 1,
    "reviews": {"$ifNull": [{"$first": "$counts.n"}, 0]},
    "ratingSum": {"$ifNull": [{"$first": "$counts.points"}, 0]}}},
  {"$set": {"averageRating": {"$cond": [
    {"$gt": ["$reviews", 0]},
    {"$round": [{"$divide": ["$ratingSum", "$reviews"]}, 2]}, null
  ]}}},
  {"$merge": {"into": "page_feedback_report", "on": "_id",
              "whenMatched": "replace", "whenNotMatched": "insert"}}
]
```

Откройте `page_feedback_report → Documents`, вставьте в **Filter** условие ниже и нажмите **Find**. У первого гида 648 отзывов с суммой 1 975 и средней 3,05. У второго число и сумма равны нулю, средней оценки пока нет.

```json
{"_id": {"$in": ["s7-page-0003", "s7-page-1024"]}}
```

## 4. Указать способ обновления, допустимое время устаревания и способ полного перестроения отчёта.

После изменения отзыва или страницы её идентификатор попадает в коллекцию `report_dirty`. Для афиши выбран предел устаревания **120 секунд**. Рабочий график предусматривает запуск каждую минуту и до минуты на ожидание и обработку. При сбое читатели продолжают видеть последний сохранённый результат.

> **Устаревание отчёта** — время между сохранением исходного изменения и появлением его результата в отчёте. Поле **since** хранит время первого ещё не обработанного изменения страницы.

Для обновления вручную выполните в WSL из корня проекта следующую команду. Она берёт отмеченные страницы, пересчитывает их группами до 128 и снимает отметки после записи.

```bash
bash scripts/lab7.sh template refresh
```

Для работы по расписанию эту строку можно поместить в `crontab -e` пользователя WSL, у которого есть доступ к Docker. В поставке запуск по расписанию оставлен на выбор владельца стенда.

```cron
* * * * * cd /mnt/c/TomeD/VSCode/Proga/Afisha/poster && bash scripts/lab7.sh template refresh
```

Для контроля откройте `report_dirty → Documents`. В **Filter** вставьте первый объект, в **Options → Sort** второй, в **Limit** укажите `1` и нажмите **Find**. Пустая выборка означает, что очередь обработана. Возраст самой старой отметки более 120 секунд означает выход за установленный предел.

```text

Sort    {"since": 1}
Limit   1
```

Если изменилась формула отчёта или исходные данные редактировали напрямую в Compass, выполните полное перестроение в WSL. Сначала результат записывается во временную коллекцию `page_feedback_report_build`. После завершения она занимает имя основной, затем обработчик перечитывает очередь.

Предоставленный `sprint-06-mongodb/compose.yaml` описывает Replica Set из трёх узлов. В стенде `template` эти три узла образуют первый шард. Добавлены второй шард, сервер конфигурации и `mongos`. Через маршрутизатор загружены 65 536 отзывов. Для запуска и проверки в WSL выполните команды из корня проекта.

```bash

bash scripts/lab7.sh template status
```

В Compass подключитесь через `127.0.0.1:27317` и откройте `visitor_feedback → Documents`. В **Filter** вставьте условие, нажмите **Explain** и выберите **Raw Output**. Значение `pageSlug` позволяет определить единственный шард для искомого отзыва.


Теперь повторите построение плана с фильтром ниже. Он находит тот же отзыв, но маршрутизатор вынужден спросить оба шарда. В подробностях плана смотрите `executionStats.executionStages.shards`. Запись о втором шарде присутствует даже при нуле найденных на нём документов.

## 7. Выбрать два сценария Redis для проекта: обязательное кэширование и одну предметную задачу; определить ключи, структуры данных, TTL и источник восстановления.

> **Кэш** хранит копию часто читаемых данных. **TTL** — оставшееся время жизни ключа. **String** хранит одно значение. **Sorted Set (ZSET)** хранит уникальных участников и сортирует их по числовому баллу.

**Карточка опубликованного гида.** Ключ `afisha:v1:page:<slug>` хранит JSON как String в течение 300 секунд. Приложение читает ключ через `GET`. При промахе источник восстановления — `event_pages`. В Compass откройте **Documents** и задайте **Filter** и **Options → Project**.

```text
Filter   {"_id": "s7-page-0003", "status": "published"}
Project  {"_id": 1, "headline": 1, "summary": 1, "sections": 1, "keywords": 1}
```

Ниже показаны команды из сценария Redis, где `page` — найденная карточка. На чтении вызывается `GET`, при заполнении — `SET` с TTL. После правки или снятия с публикации `DEL` сбрасывает копию. Кэш заполняется только для опубликованной страницы.

```lua
local cache = 'afisha:v1:page:' .. page._id
redis.call('GET', cache)
redis.call('SET', cache, cjson.encode(page), 'EX', 300)
redis.call('DEL', cache)
```

**Дневной рейтинг для редактора.** Ключ `afisha:v1:rank:{YYYY-MM-DD}:approved` — ZSET. Участник — `pageSlug`, балл — число одобренных отзывов, созданных в эти сутки UTC. Источник восстановления — `visitor_feedback`. В `Aggregations → Text` выполните расчёт за 3 сентября. Для другой даты сдвиньте обе границы.

```json
[
  {"$match": {"moderation": "approved", "$expr": {"$and": [
    {"$gte": ["$createdAt", {"$toDate": "2026-09-03T00:00:00Z"}]},
    {"$lt":  ["$createdAt", {"$toDate": "2026-09-04T00:00:00Z"}]}
  ]}}},
  {"$group": {"_id": "$pageSlug", "score": {"$sum": 1}}},
  {"$sort": {"score": -1, "_id": 1}}
]
```

По модели редактор получает обновление каждые 5 минут. Для затронутых суток обработчик собирает временный ZSET из абсолютных значений, задаёт `EXPIREAT` на 00:00 UTC дня D+8 и публикует через `RENAME`. За пустые сутки ключ удаляется. Так учитываются исправления модерации. Чтение первых десяти мест в Redis выглядит так.

```text
ZREVRANGE afisha:v1:rank:{2026-09-03}:approved 0 9 WITHSCORES
```

Стенд воспроизводит историческую выборку в ключе дня испытания для проверки срока жизни. [Расчёт рейтинга](../../mongo/lab7/pipelines/daily-ranking.json) · [Исполненные команды Redis](../../mongo/lab7/redis-sample.lua)

## 8. Сравнить ranged и hashed shard key.

> **Ranged** размещает рядом значения ключа из одного диапазона. **Hashed** сначала вычисляет хеш значения и размещает документ по диапазону этого хеша. **Chunk** — диапазон ключей, закреплённый за конкретным шардом.

Один и тот же набор из 65 536 отзывов загружен в две коллекции. Для `visitor_feedback` выбран `{"pageSlug":"hashed"}` и восемь начальных диапазонов. Для `feedback_ranged` выбран `{"pageSlug":1}` с границей `s7-page-0512`. Верхняя половина диапазона перед загрузкой перенесена на `shardB`.

В момент проверки у hashed было восемь диапазонов на стенде из шаблона и пять на самостоятельном. Число документов на каждом шарде совпало на обоих стендах.

| Измерение | Hashed · visitor_feedback | Ranged · feedback_ranged |
|---|---|---|
| Физические документы на shardA | 29 085 (44,38%) | 39 242 (59,88%) |
| Физические документы на shardB | 36 451 (55,62%) | 26 294 (40,12%) |
| Равенство по pageSlug и _id | 1 шард, 1 отзыв | 1 шард, 1 отзыв |
| Поиск только по _id | 2 шарда, 1 отзыв | 2 шарда, 1 отзыв |
| Интервал первых 16 гидов | 2 шарда, 13 878 отзывов | 1 шард, 13 878 отзывов |

Для проверки последней строки откройте в Compass **Documents → Filter** и постройте **Explain** по очереди для обеих коллекций. Правая граница исключена. При ranged весь интервал лежит на `shardA`. При hashed исходный порядок строк теряется, и диапазон приходится читать с обоих шардов.

```json
{"pageSlug": {"$gte": "s7-page-0000", "$lt": "s7-page-0016"}}
```

Для проверки физического размещения в каждой коллекции выполните в **Aggregations → Text** следующий конвейер. В этом опыте hashed распределил документы более равномерно, а ranged сократил число обращений для диапазонного чтения.

```json
[
  {"$collStats": {"storageStats": {"scale": 1}}},
  {"$project": {"_id": 0, "shard": 1, "documents": "$storageStats.count"}},
  {"$sort": {"shard": 1}}
]
```

## 9. Реализовать инкрементальное обновление предварительно рассчитанного отчёта.

> **Инкрементальное обновление** пересчитывает только затронутые группы. **Транзакция** сохраняет несколько изменений вместе. **Идемпотентность** означает, что повторная обработка даёт тот же итог.

Команда `apply` в одной транзакции сохраняет отзыв и отмечает его старую и новую страницы в `report_dirty`. Для изменения самой страницы передайте `"collection":"event_pages"`. Обработчик записывает абсолютные суммы и снимает отметку только при совпадении версии. Если выполнение прервалось между записью и подтверждением, страницу можно пересчитать снова.

Для проверки в WSL добавьте один одобренный отзыв и запустите обработчик. Пример рассчитан на исходную учебную выборку. Повторная отправка того же документа сохраняет результат.

```bash
bash scripts/lab7.sh template apply <<'JSON'
{"id":"s7-cli-verification","document":{
  "_id":"s7-cli-verification","schemaVersion":1,"pageSlug":"s7-page-0007",
  "authorAlias":"demo-editor","rating":4,"body":"Review for an editorial guide",
  "moderation":"approved","createdAt":{"$date":"2026-09-03T12:00:00Z"}}}
JSON
bash scripts/lab7.sh template refresh
```

В `page_feedback_report → Documents → Filter` найдите изменённую строку. Число отзывов вырастет с 592 до 593, сумма оценок — с 1 786 до 1 790.

```json
{"_id": "s7-page-0007"}
```

Верните учебные данные в исходное состояние. Для удаления того же отзыва служит `document:null`. После пересчёта повторите фильтр выше.

```bash
bash scripts/lab7.sh template apply <<'JSON'
{"id":"s7-cli-verification","document":null}
JSON
bash scripts/lab7.sh template refresh
```

| Отдельный автоматический опыт | Измеренный результат |
|---|---|
| Новый pending, затем одобрение с оценкой 5 | Сначала 592 / 1 786, затем 593 / 1 791. |
| Повтор после прерывания, затем смена оценки на 2 | При повторе 593 / 1 791, после правки 593 / 1 788. |
| Перенос на пустую страницу, удаление последнего отзыва | На новой странице 1 / 2, затем 0 / 0 и средняя null. |
| Создание и удаление гида без отзывов | Строка с нулями появилась, затем была удалена. |

Проверены все 1 025 строк. После полного перестроения они совпали с результатом инкрементального обновления. [Шаги и значения до и после](../../artifacts/lab7/template/incremental.json)

## 10. Оценить предполагаемый объём и срок жизни данных Redis.

> **MEMORY USAGE** оценивает память одного ключа вместе со значением и внутренними структурами Redis. Параметр **SAMPLES 0** учитывает все элементы составного значения. **МиБ** — 1 048 576 байт.

В WSL запустите измерение на данных отчёта. Сценарий открывает отдельный Redis 7.4.11, заполняет карточку и рейтинг, проверяет чтение, сброс кэша, уменьшение балла и исчезновение пустого рейтинга. Файл `redis.json` содержит результат этого запуска.

```bash
bash scripts/lab7.sh template redis
```

| Объект в замере | Наполнение | Память одного ключа | Срок жизни |
|---|---|---|---|
| Карточка гида | JSON 375 байт | 456 байт | 300 секунд |
| Дневной рейтинг | 994 гида из выборки | 93 944 байта | До 00:00 UTC дня D+8 |
| Рейтинг для прогноза | 1 000 гидов | 94 904 байта | Тот же предел |

Следующие команды Redis показывают объём и остаток срока жизни. `2026-11-23` — день зафиксированного измерения. В выборку вошли отзывы за `2026-09-03`. Сценарий использовал ключ дня испытания, чтобы измерить действующий TTL. В этом запуске он составил 639 117 секунд.

```text
MEMORY USAGE afisha:v1:page:s7-page-0003 SAMPLES 0
TTL afisha:v1:page:s7-page-0003
MEMORY USAGE afisha:v1:rank:{2026-11-23}:approved SAMPLES 0
TTL afisha:v1:rank:{2026-11-23}:approved
```

**Прогноз для выросшего каталога.** При восьми разных загружаемых карточках в секунду и TTL 300 секунд одновременно могут жить до 2 400 ключей. В учебной выборке опубликованы 768 гидов. Для модели предполагается каталог минимум из 2 400 опубликованных гидов и около 1 000 участников рейтинга в день.

| Расчёт | Формула | Результат |
|---|---|---|
| Обычный объём | 2 400 × 456 + 8 × 94 904 | 1 853 632 байта |
| Пик при пересборке одного дня | 1 853 632 + 94 904 | 1 948 536 байт |
| Бюджет данных с запасом 30% | Округление вверх от пика × 1,30 | 2 533 097 байт ≈ 2,42 МиБ |

Одновременно хранятся сегодня и семь предыдущих суток. У каждого дня фиксированный срок удаления. Бюджет относится к ключам. Память процесса, клиентских буферов, реплик и сохранения на диск оценивается отдельно. [Замер и параметры расчёта](../../artifacts/lab7/template/redis.json) · [Команда MEMORY USAGE](https://redis.io/docs/latest/commands/memory-usage/)

## 11. Самостоятельно развернуть шардированный MongoDB-кластер без предоставленного шаблона.

> **Сервер конфигурации** хранит карту размещения диапазонов. Клиент обращается к **mongos**, который по этой карте находит нужные шарды. Все адреса узлов самого кластера доступны внутри сети Docker.

В отдельном `mongo/lab7/compose.yaml` описаны маршрутизатор `router`, сервер конфигурации `cfg` и два шарда `mongo1` и `b`. Три Replica Set этого варианта имеют по одному участнику. Исходный шаблон указывает MongoDB 8.0.30. Для сопоставимости оба стенда запущены на версии проекта 7.0.45.
