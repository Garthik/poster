# Журнал архитектурных решений (ADR)

## ADR-01. PostgreSQL остаётся источником истины для транзакций

**Решение:** `users/events/venues/ticket_categories/tickets/orders/payments/refunds/ticket_scans` живут только в PostgreSQL. MongoDB не владеет местами, квотами и суммами. **Мотивация:** PostgreSQL обеспечивает атомарность оплаты/резервирования, FK, уникальные ограничения и `SELECT FOR UPDATE`. **Компромисс:** отдельный контентный сервис должен ссылаться на `pgEventId`, а согласованность между БД — eventual.

## ADR-02. Документная модель отражает паттерны чтения

**Решение:** содержательные блоки `sections` встроены в `event_pages`, а подборки и отзывы используют `pageSlug`-ссылки. **Мотивация:** страницу почти всегда показываем целиком и редактируем несколькими полями; количество текстовых секций ограничено. Количество отзывов не ограничено, текст страницы существует независимо от подборки и не должен дублироваться. **Недостаток:** MongoDB не имеет FK — нужны проверки ссылок, фоновый reconcile и обработка удаления.

## ADR-03. JSONB в PG vs самостоятельная коллекция Mongo

**Сценарий:** показать карточки опубликованных редакционных страниц с keyword `visit`, полученных из одинаковых документов.

- В MongoDB читаем `event_pages.find({status:'published', keywords:'visit'})` по индексу `(status, keywords)`; поле `keywords` — массив, Mongo создаёт multikey индекс.
- Для сравнения экспортируем **те же MongoDB документы** в PostgreSQL `app.lab5_content_compare(payload JSONB)`; выборка выполняет `payload->>'status'='published' AND payload->'keywords' ? 'visit'`.
- `scripts/lab5/compare.sh` материализует оба результата и сравнивает JSON в Python с полной проверкой совпадения и непустоты.

**Выбор:** для редакционного домена предпочитаем MongoDB, поскольку версии полей, секции текста, коллекции и отзывы автономны, а время их обновлений не связано с продажами. При небольшой статической странице, тесно связанной с карточкой события и PostgreSQL-транзакцией, **JSONB проще**: одна база, единое резервирование/доступ/транзакции. В текущей архитектуре JSONB — только сравнение, не второй источник истины. **Числа скорости** не заявлены: без отдельного benchmark честно сравниваем функциональную модель, запросы и требования к эксплуатации, а не выдумываем latency.

## ADR-04. Версионирование документов

В каждом документе есть `schemaVersion`. Чтение обязано понимать v1 и v2 в переходный период. Новое поле v2 у `event_pages` — `readingMinutes: int (1..60)`:

1. **Expand:** валидатор `mongo/schema.js` допускает v1 без нового поля и требует `readingMinutes` у v2. Новые версии сервиса сначала умеют читать оба формата.
2. **Migrate:** `./scripts/lab5.sh evolve` обновляет документы v1 -> v2, вычисляя `readingMinutes` по длине summary. Это идемпотентная миграция: повторный запуск не меняет v2.
3. **Contract:** после проверки отсутствия документов v1 можно изменить валидатор и удалить поддержку v1. В учебном стенде этот шаг выполняется только вручную, чтобы оставалась демонстрация совместимости.

Важно: `mongo/sync_from_pg.js` использует `$setOnInsert` для `schemaVersion`, поэтому повторная синхронизация событий PostgreSQL не откатывает v2 обратно к v1.

## ADR-05. CRUD и бизнес-ограничения

В `mongo/crud.js` выполняется полный C/R/U/D для всех трёх коллекций. В `mongo/validation_test.js` намеренно отклоняются нарушения бизнес-правил: опубликованная страница без достаточного описания или секций, повтор страницы в подборке, рейтинг вне диапазона 1..5. Списки ссылок дополнительно сверяются скриптом.

## ADR-06. Учебные условия и безопасность

MongoDB вынесена в отдельный Compose-проект с bind `127.0.0.1:27018`, пароль генерируется локально в приватном файле `~/.local/share/ticket-platform-ha/lab5-mongo.env`. Root используется скриптами стенда для создания коллекций. **Не выпускать в интернет**: для production предусмотреть роли MongoDB с минимальными привилегиями, TLS, backup/restore, изоляцию сетей и мониторинг.
