# Владение данными и документная модель

## 1. Источники истины

| Домен | Основной владелец | Почему | Кто может изменять |
|---|---|---|---|
| Пользователи, роли, пароли | PostgreSQL (`app.users`) | идентичность и ограничения | транзакционный backend |
| Площадки/места | PostgreSQL (`app.venues`, `venue_seats`) | FK и ограничения уникальности | backend |
| Событие, дата, статус, организатор | PostgreSQL (`app.events`) | одна атомарная картина продаж | backend |
| Цены, квоты, билеты, заказы | PostgreSQL (`app.ticket_categories`, `tickets`, `orders`, `order_items`) | транзакции, проверки overbooking | backend |
| Оплаты, возвраты, сканы | PostgreSQL (`payments`, `refunds`, `ticket_scans`) | финансовый аудит и OLAP | backend |
| Редакторские страницы: заголовок, блоки советов, ключевые слова | MongoDB (`event_pages`) | контент меняется без реляционной миграции | редакторский сервис |
| Подборки и тематические маршруты | MongoDB (`editorial_collections`) | часто меняющийся порядок и состав страниц | редакторский сервис |
| Пользовательский текстовый отзыв о материале и его модерация | MongoDB (`visitor_feedback`) | независимый жизненный цикл отзыва | контент-сервис |
| `app.lab5_content_compare` | PostgreSQL, **вторичная тестовая проекция** Mongo | контроль JSONB vs Mongo, в бою не хранится | только стенд сравнения |

Если страница Mongo ссылается на `pgEventId`, источник истины для **существования события, времени начала и цены** — только PostgreSQL. Ни в одной редакционной коллекции Mongo нет копии `orders`, `tickets`, `payments` или криптографических QR.

## 2. Три коллекции (не реляционная копия)

### `event_pages` (корень агрегата)

```json
{
  "_id": "pg-event-12",
  "schemaVersion": 1,
  "pgEventId": "12",
  "headline": "Symphony Night — гид посетителя",
  "summary": "Как подготовиться к мероприятию, маршрут и полезные советы.",
  "status": "published",
  "keywords": ["visit", "guide"],
  "sections": [
    {"heading":"Перед посещением","body":"Приходите заранее для проверки билетов."},
    {"heading":"После концерта","body":"Возвращайтесь по обозначенному выходу."}
  ]
}
```

- `sections` **встроены** в страницу: всегда читаются вместе с ней; обновление блока происходит вместе с основным документом; массив ограничен **15** блоками, текст каждого — 2000 символами. Такой ограниченный объём защищает от неограниченного роста BSON-документа.
- `pgEventId` — **ссылка на PostgreSQL, не MongoDB FK**; в документе не дублируются коммерческие свойства события.
- `status=published` требует краткое описание от 10 символов и как минимум один блок.

### `editorial_collections` (M:N)

```json
{
  "_id":"weekend-guides",
  "schemaVersion":1,
  "title":"Идеи для выходных",
  "kind":"thematic",
  "pageSlugs":["pg-event-12","pg-event-13"]
}
```

- Одна подборка ссылается на **несколько страниц**, а одна страница входит в **несколько подборок**: M:N.
- Хранятся ссылки `pageSlugs`, а не вложенные копии страниц. Причина: страницы меняются самостоятельно, одну страницу показывают разные подборки; встраивание привело бы к дублированию текста и рассогласованию.
- Ограничение `pageSlugs`: 1..20, повторения запрещены через `uniqueItems` в `$jsonSchema`.

### `visitor_feedback` (1:N)

```json
{
  "_id":"sample-feedback-1",
  "schemaVersion":1,
  "pageSlug":"pg-event-12",
  "authorAlias":"sample-reader",
  "rating":5,
  "body":"Полезная статья с советами.",
  "moderation":"approved"
}
```

- Одна страница имеет **много отзывов**, но каждый отзыв ссылается на **одну** страницу: 1:N.
- Отзывы **хранятся отдельно**. Их количество может расти без границ, у них отдельная модерация и индекс `{pageSlug:1,moderation:1}`. Встраивание отзывов бесконечно увеличивало бы `event_pages` и мешало бы независимым обновлениям.
- `rating` — целое число 1..5; статус модерации — `pending | approved | rejected`.

### Логическая схема

```text
PostgreSQL: app.events.id [BIGINT IDENTITY]
              │  cross-DB reference (string pgEventId)
              ▼
MongoDB: event_pages._id ──(1:N, pageSlug)──> visitor_feedback
                  ▲
                  │
                  └──(M:N, pageSlugs array)── editorial_collections
```

## 3. Реальные задачи, где документная модель удобнее

1. **Редакторская страница мероприятия**: смешанные информационные блоки, контентные поля и форматирование. Читается целиком, блоки редактируются совместно.
2. **Подборки по темам**: ссылки на готовые страницы, сортируемый массив членов до 20, быстрое чтение подборки без join-таблицы.
3. **Отзывы о редакционном материале**: отдельно масштабируемая коллекция с модерацией и собственными индексами.

Сущности «оплата», «резервирование последнего места», «уникальный QR» **не подходят** для переноса в Mongo в рамках работы, поскольку уже обеспечены реляционными транзакциями и ограничениями PostgreSQL.

## 4. Контроль целостности междокументных ссылок

MongoDB Schema Validation проверяет структуру, но **не** гарантирует существование документа в другой коллекции. `mongo/validation_test.js` явно проверяет все `pageSlugs` и `pageSlug` через множество `_id` страниц. Для `pgEventId` нужна периодическая сверка с `app.events.id`: сверка экспортированных событий в `scripts/lab5/sync.sh` показывает направление зависимости, но удаление события требует отдельного обработки события удаления/фоновой reconcile-процедуры.

Нет атомарного commit между двумя СУБД. В production используем Transactional Outbox в PostgreSQL и асинхронного подписчика в Mongo с идемпотентными upsert, версией изменений и повторной обработкой ошибок. В лабораторной вместо реального CDC реализован детерминированный `sync` + контроль ссылок.
